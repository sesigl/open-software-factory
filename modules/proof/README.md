# proof

Evidence for each behavior a pull request claims. proof joins the screenshots, videos, traces and test results of
your test reports by scenario ID into an evidence bundle (the `evidence-bundle` contract in
[`contracts/`](../../contracts/README.md#formats)), checks it, and shows it on the pull request as one comment and
the commit status `proof`. It also captures a running product, and runs as a GitHub Action. Decisions:
[ADR 0028](../../docs/decisions/0028-proof.md), [ADR 0029](../../docs/decisions/0029-proof-capture-and-action.md).

## Quick start

This quick start is scenario `SCN-PROOF-001` and is tested on every change. In a Git repository with at least one
commit, run your Playwright tests with the JSON reporter (`--reporter=json`) and name the scenario in the test
title. A report with one test and its trace looks like this:

```json report.json
{
  "suites": [
    {
      "title": "checkout.spec.ts",
      "specs": [
        {
          "title": "SCN-WEB-001 a guest pays with a card",
          "tags": [],
          "tests": [
            {
              "status": "expected",
              "annotations": [],
              "results": [
                {
                  "status": "passed",
                  "attachments": [
                    { "name": "trace", "contentType": "application/zip", "path": "test-results/checkout/trace.zip" }
                  ]
                }
              ]
            }
          ]
        }
      ]
    }
  ]
}
```

Then bundle it:

```sh
npx @opensoftware/proof bundle --playwright report.json --repository https://github.com/acme/web
```

It writes `$OUTPUT/evidence/evidence.json`: the commit of your repository, the scenario `SCN-WEB-001` with the result
`passed`, and the trace, copied to `artifacts/SCN-WEB-001/trace.zip`, with its kind `playwright-trace` and its
SHA-256.

## How tests become evidence

A test belongs to every scenario ID (`SCN-<PREFIX>-NNN`) in its title, the titles of its `describe` blocks, its
tags (`test("…", { tag: "@SCN-WEB-001" }, …)`) and its annotations. A JUnit test case belongs to the ID in its
property `scenario`, as the `@opensoftware/testkit` writes it, or else to the ID in its name. A test without an ID
is named on the error output (`no scenario ID: <title>`) and left out.

| Source | In the bundle | Kind |
| --- | --- | --- |
| Playwright attachment `trace` | `artifacts/<scenario ID>/<file>` | `playwright-trace` |
| Playwright attachment with an `image/*` type | `artifacts/<scenario ID>/<file>` | `screenshot` |
| Playwright attachment with a `video/*` type | `artifacts/<scenario ID>/<file>` | `video` |
| any other Playwright attachment with a file | `artifacts/<scenario ID>/<file>` | `other` |
| a JUnit report | `junit/<file>`, evidence for each of its scenarios | `junit` |

Results: a Playwright test with the status `expected` passed, `unexpected` failed, `flaky` (passed only on retry)
failed and `skipped` was skipped. A JUnit test case with `failure` or `error` failed. A scenario failed when any of
its tests failed, was skipped when all of them were skipped, and passed otherwise. The bundle passed only when every
scenario passed.

The subject of the bundle is the commit `--commit` or `HEAD` of the Git repository in the current folder, the
repository `--repository` or, in GitHub Actions, `$GITHUB_SERVER_URL/$GITHUB_REPOSITORY`, and the pull request
`--pull-request`. The bundle ID is a hash of the subject and the evidence, so the same evidence gives the same ID.
A missing report or attachment file stops the bundle and names the file.

## Verify a bundle

```sh
proof verify evidence --scenario SCN-WEB-001 --scenario SCN-WEB-002
```

verify checks `evidence.json` against the contract (`evidence.json <JSON Pointer>: <problem>`), each artifact
against its SHA-256 (`<path> does not match its SHA-256`, `<path> is missing`), and each listed scenario, or each
scenario of the bundle without `--scenario`: `<id> passed with <n> artifacts`, `<id> has no evidence`, `<id> failed`
or `<id> was skipped`. It exits 1 when any line is a problem.

## Capture a running product

Not every behavior has a Playwright test. To show a page as it is, capture it:

```sh
npx playwright-core install chromium   # once
proof capture http://localhost:3000/checkout --scenario SCN-WEB-001 --expect "Pay with a card"
proof bundle --playwright "$OUTPUT/capture/report.json"
```

capture opens the page in headless Chromium and writes `page.png` (the whole page), `video.webm` and `trace.zip`
(open it with `npx playwright show-trace`) to `$OUTPUT/capture/SCN-WEB-001/`, or below `--out`. It adds the
scenario to `report.json` there, a Playwright JSON report, so `bundle` reads a capture like a test run. A second
capture of another scenario adds it; a second capture of the same scenario replaces it. A page that answers 400 or
more (`SCN-WEB-001: <url> answered 500`), or that does not show the `--expect` text within 5 seconds
(`SCN-WEB-001: the page does not show "Pay with a card"`), is still captured, as `unexpected`, and capture exits
with code 1.

An agent that drives the product with [Playwright MCP](https://github.com/microsoft/playwright-mcp) saves its
screenshots, videos and traces with `--output-dir <folder>`, `--save-video` and `--save-trace`. Take them for a
scenario with:

```sh
proof capture --from <folder> --scenario SCN-WEB-002
```

Every `.png`, `.jpg` and `.jpeg` below the folder is a screenshot, every `.webm` a video and every `.zip` a trace;
other files are left out. They keep their paths below `$OUTPUT/capture/SCN-WEB-002/`. A folder without one of them
is refused (`<folder> has no screenshot, video or trace`).

## Attach a bundle to a pull request

```sh
PROOF_FORGE_TOKEN=$GITHUB_TOKEN proof attach evidence --pr https://github.com/acme/web/pull/7 --bundle-url "$RUN_URL"
```

attach posts one comment with the result, a link to the bundle and a table of the scenarios, and sets the commit
status `proof` on the bundle's commit to `success` or `failure` with the description `<n> of <m> scenarios passed`.
The comment starts with `<!-- proof -->`; a second attach edits it instead of adding one. The pull request is `--pr`
or the bundle's own. A URL with `/pull/<n>` is GitHub, one with `/pulls/<n>` Forgejo; `PROOF_FORGE_URL` points at
GitHub Enterprise or a Forgejo server whose API is not at the origin of the URL.

With `--store s3://<bucket>/<prefix>`, attach first uploads every file of the bundle to
`<prefix>/<bundle id>/` in an S3-compatible store and links its `evidence.json`. The store is set with the usual
`AWS_*` variables; the bucket must exist. Without `--store`, `--bundle-url` names where the bundle is, for example the
CI run that kept it as an artifact.

## GitHub Action

```yaml
permissions:
  pull-requests: write
  statuses: write
steps:
  # ... run the tests, with Playwright's JSON reporter or a JUnit reporter
  - uses: sesigl/open-software-factory/modules/proof@proof-v0.1.0
    if: always()
    with:
      playwright: playwright-report.json
      junit: reports/junit/*.xml
```

The action bundles the reports into `$RUNNER_TEMP/proof/evidence` (its output `bundle`), for the head commit of the
pull request or else `GITHUB_SHA`, and verifies it. On a pull request it then attaches the bundle with a link to
the workflow run, and uploads it as the artifact `proof` of the run. It fails when the verification failed, after
the attach, so the pull request shows why.

| Input | Default | Meaning |
| --- | --- | --- |
| `playwright` | | Playwright JSON reports, one path or glob per line. |
| `junit` | | JUnit XML reports, one path or glob per line. |
| `scenarios` | every scenario of the bundle | Scenario IDs that must pass with evidence. |
| `token` | `github.token` | Token that may comment on the pull request and set commit statuses. |
| `command` | `npx --yes @opensoftware/proof@<version>` | The proof command. The version is the one of the action's release. |

On GitHub Enterprise the action attaches through `GITHUB_API_URL`. This repository runs the action on every pull
request in the job `verify` of `.github/workflows/verify.yml`.

## Releases

release-please opens a release pull request from the Conventional Commits under `modules/proof/`. Merging it
creates the tag `proof-v<version>`, and `.github/workflows/publish-proof.yml` builds `dist/` and publishes
`@opensoftware/proof` to npm. The first release is `0.1.0`; until `1.0.0`, a breaking change raises the minor
version. The one-time setup is the same as for contracts ([`contracts/README.md`](../../contracts/README.md#releases)),
with a trusted publisher for `publish-proof.yml`. No credential is stored in the repository.
