# spec-trace

Requirements traceability for any repository with Gherkin feature files. spec-trace checks that every scenario has
one ID and one status, that every implemented scenario has exactly one test whose step labels match its steps, and
that the test passed. It writes one JSON report of every scenario, its test, its result, its evidence and the
changes since a base commit, and runs as a GitHub Action. Decisions: [ADR 0030](../../docs/decisions/0030-spec-trace.md),
[ADR 0031](../../docs/decisions/0031-spec-trace-action-and-dogfood.md).

## Quick start

This quick start is scenario `SCN-TRACE-001` and is tested on every change. In a repository with one feature
file:

```gherkin features/checkout.feature
Feature: Checkout

  @id=SCN-SHOP-001 @status=implemented
  Scenario: A guest pays with a card
    Given a cart with one book
    When the guest pays with a card
    Then the order is paid
```

and its test, which names the scenario ID and repeats its steps:

```ts tests/SCN-SHOP-001.test.ts
import { scenario } from "@opensoftware/testkit";

scenario("SCN-SHOP-001", async ({ given, when, then }) => {
  await given("a cart with one book", async () => {});
  await when("the guest pays with a card", async () => {});
  await then("the order is paid", async () => {});
});
```

run:

```sh
npx @opensoftware/spec-trace report
```

It writes `$OUTPUT/spec-trace.json` with the scenario `SCN-SHOP-001`, its status `implemented` and its test
`tests/SCN-SHOP-001.test.ts:3`. `npx @opensoftware/spec-trace check` checks the same repository and exits 1 on any
finding.

| Command | What it does |
| --- | --- |
| `check [--only <rules>] [--config <file>]` | Check the rules SPEC, TRACE, STEPS and PASS (or the comma-separated --only) on the repository in the current folder. Prints one line per finding and exits 1 when there is one. |
| `report [--out <file>] [--evidence <bundle>]... | `next-id <prefix> [--config <file>]` | Print the next free scenario ID of the prefix. |

## The rules

| Rule | What it checks |
| --- | --- |
| SPEC | Every scenario has exactly one `@id` and one `@status` (`planned`, `implemented`, `deprecated`). The ID matches the pattern and its prefix is registered for the folder of the feature file, when prefixes are configured. IDs are unique. A feature file that does not parse is a finding with its line. |
| TRACE | Every `implemented` scenario has exactly one test, every test names an existing scenario with a string literal, and a `deprecated` scenario has no test. A `planned` scenario may have a test. With `testFolder`, the test lives next to the feature files; with `conformance`, each adapter of a port has one test per scenario. |
| STEPS | The labels of the `given`, `when` and `then` calls of a test match the steps of its scenario, in order, word for word. Background steps come first, `And` and `But` take the keyword before them, and an outline parameter `<name>` matches any value. |
| PASS | The test of every `implemented` scenario ran and passed in the JUnit XML reports of the `junit` folder. Failed, skipped and missing results fail. Every example of an outline counts. |

A test is a call of the scenario function, `scenario("SCN-SHOP-001", ...)` by default. A JUnit test case belongs
to the scenario in its property `scenario`, as `@opensoftware/testkit` writes it, or else to the first ID in its
name or class name.

Each finding is one line, `RULE file:line message`; each rule ends with `RULE ok` or `RULE failed: N`. `check`
exits 0 without findings, 1 with findings and 2 when the configuration or the command line is wrong.

## The report

`spec-trace report` writes one JSON object:

```json
{
  "scenarios": [
    {
      "id": "SCN-SHOP-001",
      "name": "A guest pays with a card",
      "file": "features/checkout.feature",
      "line": 4,
      "status": "implemented",
      "examples": 0,
      "tests": ["tests/SCN-SHOP-001.test.ts:3"],
      "result": "passed",
      "evidence": 2
    }
  ],
  "totals": { "scenarios": 1, "planned": 0, "implemented": 1, "deprecated": 0, "tested": 1, "passed": 1 },
  "findings": [],
  "changes": {
    "base": "4f1c2d3e4f5a6b7c8d9e0f1a2b3c4d5e6f7a8b9c",
    "added": ["SCN-SHOP-002"],
    "removed": [],
    "status": [{ "id": "SCN-SHOP-001", "from": "planned", "to": "implemented" }],
    "steps": []
  }
}
```

`examples` is the number of rows of an outline's Examples tables; an outline counts as one scenario. `result` is
`passed`, `failed`, `skipped` or `not run`, and `null` without JUnit reports. `evidence` is the number of artifacts
of the scenario in the proof bundles given with `--evidence` (each checked against the `evidence-bundle` contract),
and `null` without them. `findings` holds the findings of SPEC, TRACE and STEPS, and of PASS when there are JUnit
reports, as objects with `rule`, `file`, `line` and `message`.

`--base <commit>` compares the scenarios with the feature files of a commit, read with Git from the repository in
the current folder. `changes` lists the scenario IDs `added` and `removed` since then, the `status` changes and the
IDs whose `steps` changed; it is `null` without `--base`. The output line then ends with
`since the base: 1 added, 0 removed, 1 with a new status, 0 with new steps`. A base that is not a commit exits 2. The
changes are for the review: no rule fails on them.

`--summary <file>` adds a Markdown summary to the end of the file: the totals, a table of the changes and a table of
the findings. In a workflow, `--summary "$GITHUB_STEP_SUMMARY"` shows it on the run's page.

## GitHub Action

```yaml
- uses: actions/checkout@v5
  with:
    fetch-depth: 0 # the base commit of the pull request, for the changes
# ... run the tests, so the JUnit reports are in reports/junit/ ...
- uses: sesigl/open-software-factory/modules/spec-trace@spec-trace-v0.1.0
```

The action writes the report with the job summary, uploads it as the artifact `spec-trace`, then runs
`spec-trace check`. It fails when a rule has a finding.

| Input | Default | Meaning |
| --- | --- | --- |
| `rules` | `SPEC,TRACE,STEPS,PASS` | The rules to check, separated by commas. Empty writes only the report. |
| `evidence` | none | Folders of proof evidence bundles, one per line. |
| `base` | the base commit of the pull request | The commit to compare the scenarios with; none on other events. |
| `out` | `$RUNNER_TEMP/spec-trace/spec-trace.json` | Where to write the JSON report. |
| `config` | `spec-trace.json` | The settings file. |
| `command` | `npx --yes @opensoftware/spec-trace@<version of the action>` | The spec-trace command. |

The output `report` is the path of the JSON report.

## Settings

An optional `spec-trace.json` in the current folder, or the file named by `--config`. Every key is optional.

| Key | Default | Meaning |
| --- | --- | --- |
| `features` | `["**/*.feature"]` | Globs of the feature files. |
| `tests` | `["**/*.test.ts"]` | Globs of the test files. |
| `junit` | `"reports/junit"` | Folder of the JUnit XML reports. |
| `id` | `"^SCN-([A-Z][A-Z0-9]*)-\\d{3}$"` | Regular expression of a scenario ID; its first group is the prefix. |
| `function` | `"scenario"` | The test function whose first argument is the scenario ID. |
| `prefixes` | none | An object of prefix and folder (`{ "SHOP": "shop/features/" }`), or a Markdown file whose table rows are `\| PREFIX \| owner \| \`folder/\` \|`. Without it, any prefix is allowed anywhere. |
| `testFolder` | none | The test of a scenario in `<root>/features/` must live in `<root>/<testFolder>/`. |
| `conformance` | none | `{ "tag": "@conformance", "ports": "ports/{port}/features/", "adapters": "adapters/{port}/{adapter}/" }`: each adapter of a port needs one test for every implemented scenario of the port with the tag. |

Files in `node_modules` and in hidden folders are never read.

## Releases

release-please opens a release pull request from the Conventional Commits under `modules/spec-trace/`. Merging it
creates the tag `spec-trace-v<version>`, and `.github/workflows/publish-spec-trace.yml` builds `dist/` and publishes
`@opensoftware/spec-trace` to npm. The first release is `0.1.0`; until `1.0.0`, a breaking change raises the minor
version. The one-time setup is the same as for contracts ([`contracts/README.md`](../../contracts/README.md#releases)),
with a trusted publisher for `publish-spec-trace.yml`. No credential is stored in the repository.
