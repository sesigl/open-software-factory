# harness-codex

Runs Codex behind the factory's harness port. The client talks ACP to `harness-codex` as to any agent; the adapter
starts Codex through its ACP bridge `@agentclientprotocol/codex-acp` behind the harness proxy. Every session runs in
Codex's mode `read-only`, which asks before each edit and each command that leaves the sandbox, a tool allowlist holds
whatever the agent tries, a cancelled turn ends within 5 seconds, and each session exports as a run record with the
tokens Codex reported. Decision: [ADR 0053](../../../docs/decisions/0053-harness-codex-opencode.md). The port's
scenarios are in [`ports/harness/features/`](../../../ports/harness/features/harness.feature).

## Quick start

Point Codex at a model gateway and let the client approve reads and edits; every other tool call is refused without
asking it:

```sh
OPENAI_BASE_URL=https://gateway.example.com/v1 OPENAI_API_KEY=<gateway key> \
  npx @opensoftware/harness-codex run --allow read,edit
```

The adapter now speaks ACP on stdin and stdout. After the session, export it:

```sh
npx @opensoftware/harness-codex transcript <session ID>
```

It writes `$OUTPUT/run-record.json` and `$OUTPUT/transcript.jsonl`.

## How it behaves

- **The harness proxy** does what every harness adapter does: sessions and prompts pass through, tool calls of kinds
  outside `--allow` are refused without asking the client, a cancelled turn that has not ended after 3 seconds is
  stopped, and each session is recorded ([`harness-proxy`](../../../packages/harness-proxy/README.md)).
- **Steering.** A prompt sent while a turn runs reaches Codex as codex-acp's request `_session/steering`, so Codex
  takes it into the running turn. Both prompts end with that turn.
- **Codex asks first.** Every session runs in the mode `read-only`: reads and commands run in a read-only sandbox
  without asking, and Codex asks before each edit (kind `edit`) and each command that leaves the sandbox (kind
  `execute`). A command in the sandbox cannot write. The proxy passes no `session/set_mode` and no
  `session/set_config_option`, so a client cannot leave that mode. The sandbox needs a Linux sandbox (bubblewrap or
  Landlock) or macOS Seatbelt; without one every sandboxed command fails.
- **Its own settings.** Codex keeps its settings, logins and sessions in `OSF_DATA/codex`, never in the user's
  `~/.codex`. On each `run` the adapter writes `config.toml` there with one model provider and nothing else.
- **The model gateway.** Codex calls the Responses API at `OPENAI_BASE_URL` with `OPENAI_API_KEY` and the model
  `OPENAI_MODEL`.
- **The run record** has `osf.harness.name` `codex`, `osf.harness.version` the bridge's version and the tokens of all
  turns in `gen_ai.usage.*`. Codex reports no cost.
- **Titles.** After the first turn of a session Codex asks the model once more, for the session's title.

## Commands

| Command | What it does |
| --- | --- |
| `harness-codex run [--allow <kinds>]` | Start Codex and run the adapter on stdio until Codex exits. |
| `harness-codex transcript <session ID>` | Write the session's run record to `$OUTPUT/run-record.json` and its transcript to `$OUTPUT/transcript.jsonl`. |

## Releases

release-please opens a release pull request from the Conventional Commits under `adapters/harness/codex/`. Merging it
creates the tag `harness-codex-v<version>`. The workflow `.github/workflows/publish-harness-codex.yml` then builds the
package and publishes it to npm as `@opensoftware/harness-codex`. The first release is `0.1.0`; until `1.0.0`, a
breaking change raises the minor version. The one-time setup is the same as for contracts
([`contracts/README.md`](../../../contracts/README.md#releases)). No credential is stored in the repository.

## Scenarios

The adapter passes every `@conformance` scenario of the harness port and its own scenarios in `features/`, against
the real Codex with the testkit's model gateway.
