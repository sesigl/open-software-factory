# 0020. factory-spec renders, plans and applies factory.yaml

## Context

T-03 starts wave 1. A factory is declared in `factory.yaml` (the `factory-definition` contract, ADR 0006), with
Markdown prompts and skills next to it. Every harness reads its own files: Claude Code reads `CLAUDE.md`,
`.mcp.json` and `.claude/skills/`; Codex reads `AGENTS.md`, `.codex/config.toml` and `.agents/skills/`; OpenCode
reads `AGENTS.md`, `opencode.json` and `.opencode/skills/`. Teams keep these files in step by hand. The
architecture (docs/architecture/internals.md) copies Terraform's pillars: desired state, providers pinned in a lock
file, plan, apply and drift. This repository links its skills with a hand-written script (`make agents-sync`).

## Decision

- A new core module `modules/factory-spec`, package `@opensoftware/factory-spec`, CLI `factory`, scenario prefix
  `FSPEC`. Layers: `entry` (`src/cli.ts`) → `commands` → `adapters` → `domain`.
- `factory lint` validates `factory.yaml` against the contract and adds the rules a schema cannot express: every
  harness and secret provider is declared under `providers`, every referenced file exists, every stage names an
  agent. Each problem is one line `file:line:column message`.
- `factory render` writes the files of one agent for its harness, or with `--harness all` for every harness under
  `providers.harness`: `AGENTS.md` from the prompt, `CLAUDE.md` (`@AGENTS.md`), `.mcp.json`, `.codex/config.toml`,
  `opencode.json`, and one relative symbolic link per skill in each harness's skill folder. Links into a skill
  folder that the factory no longer declares are removed. The model is not written: the inference gateway routes
  it at run time, so model aliases such as `routes/triage` never reach a harness.
- MCP servers: `<package>@<version>` is an npm package started with `npx -y` over stdio.
  `registry:<name>@<version>` is a server in the MCP Registry (API v0.1, `FACTORY_MCP_REGISTRY`, default
  `https://registry.modelcontextprotocol.io`). `factory plan` resolves the version range once and pins the exact
  version, its package or remote URL in `factory.lock`. Render and later plans read only the lock, never the
  registry. A registry server without a lock entry is an error that names `factory plan`.
- `factory plan` compares the resolved definition with the last applied one and prints one line per changed
  value (`~ agents.triage.model: "a" -> "b"`), plus one line per rendered file changed by hand since the last
  apply (drift). `factory apply` renders the files and stores the applied definition and file hashes in the state
  folder `OSF_DATA` and prints a digest of what it applied. Rolling back is applying an older version. `factory diff <old> [new]` compares two versions,
  as files or Git revisions (`HEAD~1:factory.yaml`). `factory resolve` prints the resolved definition: defaults
  filled in and MCP versions pinned, still a valid `factory-definition` document. The same function is the
  package's library export.
- The README's Commands section is generated from `factory --help` by `make docs` (marker
  `generated by make docs from src/cli.ts --help`), and DOCS-GEN keeps it equal.
- This repository declares itself in `factory.yaml`. `make agents-sync` runs `factory render --harness all`, which
  produces the skill links of every harness.
- Not in this batch: webhooks on a forge and their drift, Kubernetes manifests (`render --k8s`) and gh-aw
  workflows. They follow in the next T-03 pull request.

## Options considered

| Option | For | Against |
| --- | --- | --- |
| Build factory-spec on the contract | Reads the format every module shares; plan, lock and drift as in the architecture | A new module to maintain |
| Adopt Ruler or rulesync and generate their input | Mature renderers for many harnesses | Their own source folders (`.ruler/`, `.rulesync/`), no lock, no plan, no drift, no factory with several agents |
| Extend `make agents-sync` | Already there | A repository script, not a tool other teams can use |

## Prior art

- Ruler, `@intellectronica/ruler` (MIT, active, version 0.3.x): renders rules from `.ruler/` into the files of
  many agents and manages MCP settings. Not adopted: it reads its own folder instead of a factory definition and
  has no lock, plan or drift. Its list of harness file locations was a useful check.
- rulesync (MIT, active): the same idea from `.rulesync/`, including `.mcp.json` per tool. Not adopted for the same
  reasons.
- Terraform and OpenTofu (BUSL and MPL-2.0, active): the model for plan, apply, lock and drift. Too heavy as a
  dependency for a file renderer; an OpenTofu provider can come later (internals.md).
- gh-aw (MIT, active) and kagent (Apache-2.0, active): later render targets, not inputs.
- `yaml` by eemeli (ISC, active, YAML 1.2 by default, keeps source positions): adopted to read `factory.yaml` and
  name the line of each problem. js-yaml (MIT) parses YAML 1.1 by default and turns the key `on` into `true`.
- `semver` (ISC, npm, active) with its types `@types/semver` (MIT, DefinitelyTyped): adopted to pick the highest
  registry version inside a range.
- The MCP Registry (API v0.1, preview): consulted at plan time only, as the architecture says (pin, never live).

## Consequences

- Every harness of a team reads the same prompt, skills and MCP servers; a change to `factory.yaml` reaches all of
  them through one `factory apply`.
- A registry outage cannot break render or apply, because both read only the lock.
- The state folder is local. A team that runs plan in CI points `OSF_DATA` at a folder it keeps between runs.
- Revisit the npm form of MCP servers when a server needs another runtime (for example `uvx`), and the state
  location when a forge or a cluster becomes the source of applied state.
