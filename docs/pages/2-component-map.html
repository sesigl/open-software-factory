Architecture proposal · follows the Software Factory Blueprint

Open Software Factory Map

The blueprint split into small open-source tools that each solve one problem on their own and connect through a few open formats. Where a good project already exists, the factory adopts it and builds only an adapter.

5 shared formats 11 tools to build 1 distribution that wires them 16 existing projects to adopt 4 release waves

Snapshot from 2026-10-18. The Markdown documents in this repository are the source of truth and win where this page differs. Changed since: TypeScript is the only core language (ADR 0009), and the monorepo tooling is pnpm workspaces with Turborepo, not Nx (ADR 0010).

01Rules for the tool family

These rules keep every tool independent. Check each new tool against them before it gets its own repository.

  • Formats connect the tools, not importsTools exchange data only through the shared formats in section 03. No tool imports another tool's code, so any one of them can be replaced.
  • Useful alone on day oneEvery tool solves a problem for a team that uses no other tool from the family. If it needs a sibling to be useful, it is part of that sibling.
  • Files and CLI first, server secondEach tool works on local files and in CI, for example as a GitHub Action. A server mode is optional. This makes adoption a five-minute decision.
  • Adopt the core, own the adapterSandboxes, gateways, workflow engines, trace stores and benchmark runners already exist. The family builds only the part that is specific to a coding-agent factory.
  • Prove it on ourselves firstEach tool runs in this company OS before its first public release. The repository already holds early versions of several of them.
  • One problem, one name, one releaseEach tool has its own version, changelog and documentation, and its name says what it does.

03Five shared formats

These formats are the real product. Three already exist and are adopted as they are; two are new and small. Each new format lives in its own repository with a JSON Schema and test fixtures.

04Tools to build

Eleven tools, each with what it does alone, what it reads and writes, what it adopts, and the prior art checked before deciding to build. “Seed” is what already exists in this repository.

factory-spec

buildwave 1 · TypeScript

The factory definition: a schema, a validator and a CLI (lint, diff, render).

Useful alone
One source of agent configuration for many harnesses: render writes AGENTS.md, CLAUDE.md, .mcp.json, Codex config and gh-aw workflows from one file, and lint catches broken references in CI.
Reads → writes
factory.yaml → harness config files, a resolved definition for the foreman
Prior art
Warp's factory.yaml is closed and in beta. gh-aw defines single GitHub workflows, not a factory. AGENTS.md is prose with no schema.
Seed
orchestration/workflow.config.json, agents/*/ definitions

runlog

buildwave 1 · Python

Reads the session stores of coding harnesses and exports each session as an OpenTelemetry run record.

Useful alone
Send every Claude Code, Codex or OpenCode session of a team into Langfuse or Grafana with one command, with cost and a link to the PR.
Reads → writes
harness transcript files → run record (OTLP)
Adopts
OTel SDK and GenAI conventions; Agent Trace
Prior art
Viewers such as Claudescope and agentlogs show sessions but do not export a standard. Harnesses emit their own telemetry, but not one common transcript format. Check native OTel coverage of each harness before writing a reader for it.
Seed
scripts/observability/hermes_transcript.py

proof

buildwave 1 · TypeScript

Captures what an agent verified and attaches it to the pull request as an evidence bundle.

Useful alone
Any PR, from an agent or a person, shows screenshots, a video and test results for each claimed behavior, as a PR comment and a check run.
Reads → writes
Playwright runs, test reports → evidence bundle, PR comment, check
Adopts
Playwright, Playwright MCP for computer use
Seed
qa-scenarios skill, human-feedback-batch

spec-trace

buildwave 2 · TypeScript

Links Gherkin scenario IDs to tests, evidence and pull requests, and fails CI on missing, duplicate or dangling links.

Useful alone
Requirements traceability for any repository with feature files, without executing Gherkin.
Reads → writes
feature files, tests, evidence bundles → report, required check
Prior art
Cucumber tools execute scenarios; none found that lint ID traceability across tests and PRs.
Seed
make specs-check, make traceability-check, scripts/lib/gherkin.ts

scorekit

buildwave 2 · Python

A pack of scorers for coding-agent sessions, with sampling and judge calibration.

Useful alone
Grade a team's agent sessions on redundant tests, scope creep, skipped checks, needless questions to people and change requests, and know how far each judge agrees with human labels.
Reads → writes
run records → scores
Adopts
Langfuse evaluators as the runtime (MIT, self-hostable); runs as a CLI over runlog files without it
Prior art
Eval platforms provide the judge machinery but not scorers for coding sessions, and rarely calibration.

ledger

buildwave 2 · SQL + Grafana

Joins model spend, sandbox compute, runs and PRs into flow and cost metrics.

Useful alone
An AI engineering dashboard: cost per PR by source, user, agent and model; human interactions per PR; cycle-time segments; revert rate.
Reads → writes
gateway spend logs, run records, forge events → SQL views, Grafana dashboards
Adopts
Postgres or ClickHouse, Grafana, LiteLLM spend logs
Seed
metrics pipeline (metrics.event, ADR 0029), company-metrics dashboard

taskcapture

buildwave 3 · Python

Turns a merged PR or a completed run into a replayable benchmark task, then turns benchmark results into routing rules.

Useful alone
A private benchmark from the team's own work in an afternoon, with a correctness-against-cost chart per model and harness.
Reads → writes
PR + base commit + run record → Harbor task; Harbor results → report, LiteLLM routing config
Adopts
Harbor (runs Claude Code, Codex, OpenHands and others in Docker, Daytona, Modal or E2B)
Prior art
Harbor runs tasks but does not create them from your history; that gap is the tool.

observer

buildwave 3 · Python

Groups repeated failures from scores and opens a pull request against the factory definition with the problem, the fix and the evidence, then checks the effect after the merge.

Useful alone
Point it at session logs and the agent instructions of a repository; it proposes reviewed fixes and later reports whether the failure rate fell.
Reads → writes
scores, run records, factory definition → pull request, before/after report
Prior art
backpass already edits AGENTS.md from transcripts with a review gate. Use or extend it for instruction files; build only what it lacks: scorer input, the full factory definition and the before/after check.
Seed
the agent-cleaner agent and the efficiency-ticket skill

gatekeeper

buildwave 3 · TypeScript

Decides which gate a change needs and collects the human decision where people already work.

Useful alone
Approvals for any automation or CI job: a policy picks the approver by risk class, the request goes to Slack or GitHub, and the decision is recorded with the person's identity.
Reads → writes
change summary + policy → approval request; decision → signed record, workflow signal
Adopts
OPA or Cedar for policy; Vercel Chat SDK for the message
Prior art
check first earlier human-approval SDKs for agents existed; confirm none fits before building.
Seed
docs/company/controls.json, merge gates in wf.sh pr merge

intake

buildwave 4 · TypeScript

Turns messages, issues, labels, CI failures and error reports into one stream of work item events, and offers a Factory MCP server and an API to submit work.

Useful alone
One deduplicated inbox for agent work from all tools, with a link back to where each request started.
Reads → writes
chat, tracker, forge and monitoring webhooks → work item events
Adopts
Vercel Chat SDK adapters (Slack, Teams, GitHub, Linear and others), MCP SDK; Jira and Sentry through their webhooks

foreman

build thinwave 4 · TypeScript

Runs the stages that the factory definition declares as durable workflows: starts the sandbox, drives the harness, waits at gates, records state.

Useful alone
Run any declared multi-agent pipeline with retries, pauses and human gates, without writing workflow code.
Reads → writes
work item events + factory definition → sandbox runs, gate requests, run state
Adopts
Temporal; kubernetes-sigs/agent-sandbox or E2B; harnesses through ACP or Coder's agentapi
Prior art
OpenHands Cloud covers much of this as one product. Keep foreman thin and support OpenHands as one harness, so the family stays usable piece by piece.
Seed
scripts/workflow/wf/next_action.py, ticket lifecycle in workflow.config.json

open-software-factory is not a twelfth tool. It is the distribution: a Helm chart and a Compose file that wire the tools and adopted projects together, plus a reference factory.yaml with the loop from the blueprint.

06Value from combinations

Each tool is useful alone. Each combination adds a capability, so teams can adopt the family step by step and reach the full factory without a big switch.

  • runlog
    See every agent session of the team in one place.
  • runlog + scorekit
    Know where agents waste time and money, with calibrated judges.
  • runlog + scorekit + observer
    Agent instructions that improve themselves through reviewed PRs.
  • runlog + ledger
    Cost per PR, by source, person, agent and model.
  • taskcapture + Harbor + LiteLLM
    Model choice by evidence from your own work, applied as routing rules.
  • proof + spec-trace
    PRs that prove they meet named scenarios.
  • factory-spec + foreman + gatekeeper + intake
    The delivery loop, running in the cloud with human gates.
  • all of them
    The open software factory: a closed loop that measures and improves itself.

07Release plan

Tools that produce data come first, because everything else reads their data and they have the widest audience. The orchestration pieces come last, when there is evidence to steer them.

Wave 1 · Record

The formats and the tools that write them.

  • factory definition + evidence bundle schemas
  • factory-spec
  • runlog
  • proof

Wave 2 · Measure

Read the recorded data.

  • scorekit
  • ledger
  • spec-trace

Wave 3 · Improve

Act on the measurements, behind human gates.

  • taskcapture
  • observer
  • gatekeeper

Wave 4 · Automate

Close the delivery loop.

  • intake
  • foreman
  • open-software-factory distribution

08Decisions for you

Each item has a recommendation. Nothing here is decided yet.

  • License: Apache-2.0 for every tool.It includes a patent grant, which companies prefer for infrastructure. MIT is the simpler alternative.
  • Repositories: one monorepo with independent packages and releases.Shared CI and schemas while the formats still change; split a tool out when it gets its own maintainers.
  • Languages: TypeScript for integration tools, Python for evaluation tools.MCP, Chat SDK and ACP are strongest in TypeScript; Harbor, Langfuse evaluators and judge tooling are Python.
  • Foreman: build thin on Temporal instead of adopting OpenHands as the core.Adopting OpenHands is faster but ties the family to one product. Support it as a harness instead.
  • Timing against the Lautlinge pilot.ADR 0119 puts validation before OS growth. Wave 1 tools can grow out of work this repository already does; a separate open-source program needs its own budget decision.
