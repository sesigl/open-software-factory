Open Software Factory Internals

How the tools plug into real systems, how the factory is declared in code, which loops run inside it, how the parts talk to each other, and how the principles become checks that run automatically.

10 ports with adapters 3 nested loops 6 protocols, each with one job 15 principles with a check each

Snapshot from 2026-10-18. The Markdown documents in this repository are the source of truth and win where this page differs. Changed since: TypeScript is the only core language (ADR 0009), and the monorepo tooling is pnpm workspaces with Turborepo, not Nx (ADR 0010).

00Short answers

1Adapters

Each tool defines a small interface (a port) for every outside system it touches: harness, sandbox, chat, tracker, forge, model, secrets, telemetry. An adapter implements one port for one product, such as Claude Code, Kubernetes or Teams, and must pass the port's shared conformance tests.

2Factory as code

Don't invent a language. Use YAML with a JSON Schema, and copy Terraform's four pillars: desired state, providers, plan and apply with drift detection, and reusable modules. It runs as a CLI for small setups and as a Kubernetes operator, using the kagent and agent-sandbox resources, for large ones.

3The agentic loop

Three loops are nested. Inside a harness, the model calls tools until the task is done (seconds). The foreman runs the stages as a durable workflow (hours). The improvement loop changes the factory from scores (days). All major harnesses now emit OpenTelemetry, but not in the same shape: Gemini CLI natively, Codex and OpenCode in their own formats, and Claude Code with traces in beta. runlog makes them uniform.

4Communication

Each protocol has one job. MCP is for what a model calls, ACP for driving a harness, REST for program-to-program commands, CloudEvents on a bus for facts, and OTLP for telemetry. There is no central registry to build: upstream catalogs (the MCP Registry, the ACP Registry, OCI registries) are consulted at plan time, and factory.yaml pins exact versions. Git is the registry of what is in use.

5Principles in practice

A principle counts only when a script enforces it. Each principle in section 05 has a practice and an automatic check in CI or at runtime. This repository already works this way, for example scripts instead of prose for merges and metrics.

01Ports and adapters

An adapter is its own package, for example @osf/harness-claude-code, with its own version. A port ships a conformance test kit, like Terraform provider acceptance tests; an adapter that passes it is listed. Abstract only where teams really differ: the workflow engine (Temporal) stays fixed, because an abstraction over it would cost more than it gives.

02Everything in code

The tools already exist. Terraform and OpenTofu (HCL), Pulumi (general languages), Kubernetes resources with GitOps (Argo CD, Flux), and for agents specifically kagent (resources Agent, ModelConfig and MCPServer) and Docker Agent (agent teams in YAML). The factory reuses their ideas and, where it fits, their engines.

The four pillars, taken from Terraform

PillarIn TerraformIn the factory
Desired stateHCL files in Gitfactory.yaml plus prompts and skills as Markdown, policies as Rego, all in one repository. Secrets appear only as references.
ProvidersPlugins per cloud, pinned in a lock fileAdapters per port, declared in providers: and pinned in factory.lock with versions and image digests.
Plan, apply, driftplan shows the diff; apply reconciles; state records realityfactory plan shows what changes (new agent, model change, new webhook). factory apply registers webhooks, writes harness configs, sets gateway routes, upserts scorers. A nightly plan reports drift, such as a webhook changed by hand.
ModulesReusable, versioned building blocksStage packs, for example osf/modules/code-review@1.2, with their agent, prompts, scorers and gate.

Three more pillars make the code trustworthy. Every run records the hash of the factory version it ran on. Schemas are checked in CI. Changes go through the same reviewed pull request as product code.

Example (illustrative)

version: 1
factory: web-app
providers:
  harness:   { claude-code: "^2", codex: "^1" }
  sandbox:   { kubernetes: "^0.4" }
  channel:   { slack: "^1", github: "^1" }
  inference: { litellm: "^1" }

    harness: claude-code
    model: routes/triage            # routing rule, not a fixed model
    prompt: ./agents/triage.md
    mcp: [registry:io.github/github@1.4, linear@2]
    secrets: [ref:openbao/linear-token]
    sandbox: { template: small, egress: [api.linear.app] }
  implement:
    harness: codex
    model: routes/implement
    prompt: ./agents/implement.md
    skills: [./skills/testing]
    sandbox: { template: node-22, cpu: 4, memory: 8Gi }
workflow:
  - stage: triage
  - stage: spec
    gate: { policy: ./policy/spec.rego }   # who must approve
  - stage: implement
  - stage: review
  - stage: verify
    evidence: required
automations:
  - on: github.issue.labeled(auto-implement)
  - on: sentry.fatal
  - cron: "0 10 * * *"   run: self-triage-report
scorers:
  redundant-tests: { sample: 0.2, judge: ./scorers/redundant-tests.md }

03The loops and their telemetry

The “agentic loop” is three loops nested inside each other. Each has its own engine and its own record.

  • Inner loop · seconds to minutesThe harness loopSame basic pattern in Claude Code, Codex, OpenCode and Gemini CLI:
    1. Build context: system prompt, instructions such as AGENTS.md, task, files.
    2. The model answers with text or tool calls.
    3. The harness checks permission (hooks, allowlists) and runs the tools: read, edit, shell, MCP.
    4. Results go back into the context; compact it when it grows too large.
    5. Repeat until the model stops, a budget runs out, or a person interrupts.
  • Outer loop · hoursThe delivery loop (foreman)A Temporal workflow per work item:
    1. Each stage is an activity that starts an inner loop in a fresh sandbox.
    2. Between stages: deterministic checks such as CI, tests and spec-trace.
    3. Gates wait for a signal from gatekeeper; timers handle timeouts.
    4. Steering and handoff arrive as signals into a running stage.
    5. Sub-agents are child workflows; crashes resume from history.
  • Meta loop · daysThe improvement loopRuns offline on recorded data:
    1. scorekit scores sampled runs.
    2. observer groups repeated failures and opens a pull request to the factory.
    3. taskcapture benchmarks the change, or a model choice, on real tasks.
    4. A person merges; the foreman loads the new version.
    5. The same scorer checks whether the failure rate fell.

Do the harnesses speak OpenTelemetry?

HarnessStatusWhat you get
Gemini CLInativeLogs, metrics and traces to any OTLP endpoint; reported to follow the GenAI conventions.
Codex CLInativeLogs and traces through the [otel] config. Spans are internal (session loop, responses); conversation details arrive as span events; prompt text is off by default.
Claude Codetraces in betaMetrics and log events natively. Traces need CLAUDE_CODE_ENHANCED_TELEMETRY_BETA and OTEL_TRACES_EXPORTER: an interaction span with model-request and tool spans.
OpenCodeexperimentalTraces over OTLP/HTTP behind an experimental flag; plugins, including one for Langfuse.
Claude Agent SDK and APIpublic betaAnthropic platform traces for the Messages API, Managed Agents and SDKs (since October 14, 2026).
Goose and othersnot checkedCheck per release; fall back to reading the session files.

So every major harness emits OpenTelemetry, but with different span names, mostly outside the GenAI conventions, and with content off by default. runlog closes the gap in three steps:

  1. Correlate at launch. The foreman starts each harness with OTEL_RESOURCE_ATTRIBUTES=factory.version=…,work_item.id=…,run.id=…,stage=…, so all native telemetry carries the same keys.
  2. Normalize in the Collector. A per-harness mapping in the OpenTelemetry Collector renames spans and attributes to the GenAI conventions.
  3. Complete from the session file. When the stage ends, runlog reads the harness's session file and attaches the full transcript. Telemetry alone usually leaves out content.

04How the parts talk

Six protocols, each with one job. A component never calls another component's database or imports its code.

Which protocol for which job

ProtocolJobWhere it is used
MCPWhat a model can callTools inside the sandbox, through the MCP gateway that enforces each agent's allowlist and adds credentials. The Factory MCP server lets an outside agent, such as Claude Code on a laptop, submit work and read run status. A tool may add an MCP face for agents, for example “why did this run fail?”.
ACPDrive a harnessForeman to harness: start a session, send messages, approve tool calls, stream progress, cancel.
REST (OpenAPI)Commands between programsEvery tool's server mode: submit work, request a gate decision, upload evidence, query runs and scores. Generated clients for TypeScript and Python.
CloudEvents on a busFacts that others react toNATS JetStream by default; webhooks when there is no bus. Events are past tense and versioned, for example run.completed@v1.
OTLPTelemetryHarnesses, gateways and tools to the Collector, then to any backend.
A2AAgents of other organizationsNot needed at first. Add it when factories must hand work to outside agents. Signed agent cards exist; a shared registry is still in progress.

05Principles in practice

A principle without a check is a wish. Each row names the practice and the automatic check that enforces it. The first ones protect independence, the later ones trust and cost.

PrinciplePracticeAutomatic check
Enforce by script, not proseEvery rule that matters runs as code: gates, merges, releases, metric eventsCI fails on a rule written only as text where a check could exist (review checklist item; this repository already works this way)
Declare, then reconcileAll factory state in Git; changes only through factory applyNightly factory plan; drift opens a ticket
Formats over codeTools share only versioned schemas and eventsSchema breaking-change check in CI; a dependency check forbids imports between tools
Ports with conformanceEvery outside system behind a portAn adapter must pass the port's conformance kit before it is listed
Useful aloneEach tool has a five-minute quick start without a server or a sibling toolCI runs the quick start in a clean container on every release
Adopt before buildEvery new tool or adapter records the prior art it checkedThe repository template requires a “prior art” section in the ADR; review rejects it when empty
Open standards at every boundaryMCP, ACP, OpenAPI, CloudEvents, OTLPPublic interfaces are generated from OpenAPI and AsyncAPI specs; review rejects custom wire formats
Record and correlate everythingEvery run carries run.id, work_item.id and factory.versionIngest rejects records without them; the dashboard shows the share of spend that is not attributed
Least privilege by defaultNo secrets in sandboxes; egress and MCP allowlists per agentPolicy tests in CI; a prompt-injection task in every benchmark suite
Humans at the gatesGate policy as code, chosen by risk classMerge is blocked without a signed approval record
Evidence or it didn't happenNo PR is ready without an evidence bundle for its scenariosspec-trace and proof are required checks
Measure before you changeEvery factory change shows a score or benchmark comparisonA bot comment on the factory PR; merge rule requires it
Cost is visible and boundedA budget per run and per work item at the LLM gatewayGateway stops at the budget; the ledger alerts on cost per PR over target
Every change can be undoneVersions are immutable; rollback is a revert commitRuns reference the version hash; a rollback drill runs in CI each release
Run it on ourselves firstEvery release runs in our own factory before it is publishedThe release gate requires a time in the dogfood environment with no new failing scorer
