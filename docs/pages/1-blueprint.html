01What a software factory is

The definition the talk commits to (03:31–04:13). Every principle and requirement below follows from these three properties.

PropertyMeaningConsequence for the blueprint
An agentic loopHumans and agents work together in a loop: idea or bug → triage → spec → implement → review → verify → ship → monitor → new work. Humans touch the loop at spec review, code review and product review.Feature F01, orchestration (F07), human gates.
Runs in the cloud“You can't have a local software factory”: automations cannot run on laptops, and local agents cannot be governed.Cloud runtime and sandboxes (F02), central context (F05).
Measurable and improvableThe factory itself is a system you engineer: factory engineering. It must get better over time.Factory as code (F03), metrics (F10), scoring (F11), self-improvement (F12), benchmarks (F13).

03Leading principles

Seventeen principles that hold across nearly every area of the factory. Each names its evidence in the talk and the areas it governs. Use them to decide cases the requirements do not cover.

P1

Close the loop

Work flows from intake through triage, spec, build, review, verification and shipping to monitoring, and monitoring creates new work.

An open pipeline cannot learn. The loop is what turns output into feedback.

03:43 · 04:13–04:42
loopautomationmetrics
P2

Run in the cloud, not on laptops

The factory, its agents and its automations run in a central, always-on environment.

Laptops bottleneck work on people, cannot run automations and cannot be governed.

02:48 · 03:49
runtimeaccess
P3

Declare the factory in code

Agents, prompts, MCP servers, skills, secrets, repositories, models, runners, automations and scorers are versioned files. The UI only shows them.

Only code can be tested, rolled back, reviewed and changed by agents through a pull request.

05:51–06:19 · 09:35 · 15:16 · 21:56
all areas
P4

Open and pluggable

Any model, any harness, any inference provider, any compute. Every layer can be replaced without rebuilding the others.

The best model and harness change every month. A closed stack cannot follow the evidence.

05:23–05:35 · 06:51–07:01 · 23:07–23:22
inferencecomputeorchestration
P5

Meet people where they work

Work enters and is followed from the chat, tracker, forge and devices people already use. Everything is API-driven; the factory UI is one surface among many.

Adoption at scale depends on fitting existing tools, not replacing them.

05:39 · 10:31–11:10 · 24:16–24:27
accessintegration
P6

Centralize context, record everything

Every run stores its transcript, trace, artifacts and links to its origin, issue and pull requests, in one place.

Visibility, scoring, benchmarks and self-improvement all start from the recorded run.

11:03 · 12:56–13:19 · 22:25–22:45
datavisibilityimprovement
P7

Own your data

Run data stays in systems the company controls, on its own compute and inference gateway when required.

If producing software is core to the business, the data that improves it is a core asset.

06:19–06:55
datasecurity
P8

Measure, don't trust vibes

Decide models, harnesses and workflows with evidence from your own work: online scores and your own benchmarks, not public leaderboards or social media.

Public benchmarks measure general intelligence, not your codebase; commentators have conflicts of interest.

07:08–07:53 · 21:16–21:37
scoringbenchmarksrouting
P9

Humans at the gates, agents in between

Explicit human touchpoints (spec, code, product) and deterministic gates guard the stages. Agents use their intelligence to route work inside the allowed paths.

Determinism gives control; intelligence gives speed. Each has its place.

04:26–04:36 · 08:17 · 23:41–23:48
orchestrationloop
P10

Prove the work

A change is done when the factory shows evidence that it works: computer-use verification, screenshots, video, test results.

Without proof, review becomes trust, and throughput becomes slop.

04:36 · 12:01–12:09
verificationreview
P11

Sandbox and govern centrally

Agents run in isolated sandboxes with only declared secrets and MCP servers, under role-based access, with every action attributed.

A compromised local agent acts as the logged-in person. A sandboxed one cannot.

03:08–03:31 · 09:54 · 22:45–22:59
runtimesecurityaccess
P12

One workflow, many triggers

Work from people and work from automations (schedules, webhooks, labels, CI failures, error reports) go through the same declared workflow or a declared variant.

One path means one place to measure, govern and improve.

17:22–17:58
automationloop
P13

Cost is a first-class metric

Know the cost per pull request, attributed by source, person, agent and model, and have a plan to lower it. Trade quality against cost explicitly.

Without attribution, AI spend grows faster than the value it buys.

13:47–14:06 · 20:51–21:06
metricsbenchmarksrouting
P14

Guard quality while you speed up

Every speed or cost gain is read next to a quality signal such as revert rate or change-requested rate.

Lower cost and more PRs mean nothing if the output is slop.

02:28 · 25:19–25:39
metricsoutcomes
P15

Improve the factory through the factory

Repeated failures become pull requests to the factory definition, with problem, solution and evidence, merged by a human.

The factory gets better every week without a person finding each problem.

15:28–17:11
improvementfactory as code
P16

Templates, not one process

The loop is a template that each team and product surface adapts; the factory supports variants, also beyond software.

One fixed process fits no real company.

04:42–05:07 · 09:16
looporchestration
P17

Two jobs: build product, build the factory

Product engineers deliver value through the factory. Factory engineers tune the factory: skills, MCP servers, model mix, workflow.

Improving the machine is real work with its own owner, or it does not happen.

@context=factory-loop @owner=factory-engineering
Feature: The factory loop
  A software factory is a closed agentic loop in which people and agents work together:
  work enters, is triaged, specified, implemented, reviewed, verified, shipped and monitored,
  and monitoring feeds new work back into the start of the loop.

  Rule: Work enters the loop from people and from production signals

    @scenario_id=SCN-FACTORY-LOOP-001 @status=planned @evidence=spoken @source=04:13
    Scenario: A person submits a new product idea
      Given a factory for the product surface "web app"
      When a product engineer submits the idea "Export reports as CSV" from a connected surface
      Then the factory creates exactly one work item for the idea
      And the work item enters the "triage" stage

    @scenario_id=SCN-FACTORY-LOOP-002 @status=planned @evidence=screen @source=03:40
    Scenario: A bug report enters the same loop as an idea
      Given a factory for the product surface "web app"
      When a user reports the bug "Export button does nothing on Safari"
      Then the factory creates a work item of type "bug"
      And the work item follows the same loop as a product idea

    @scenario_id=SCN-FACTORY-LOOP-003 @status=planned @evidence=screen @source=03:40 @source=04:42 @source=17:30
    Scenario: Monitoring feeds new work back to the start of the loop
      Given the factory watches production error reports
      When a new fatal error is reported for a shipped change
      Then the factory creates a work item that links the error report and the change
      And the work item enters the "triage" stage

  Rule: Each stage has a defined owner and hands its result to the next stage

    @scenario_id=SCN-FACTORY-LOOP-004 @status=planned @evidence=screen @source=04:19 @source=09:58
    Scenario: Triage classifies new work and sets its task state
      Given a new work item in the "triage" stage
      When the triage agent finishes
      Then the work item has a type, a priority and a task state
      And the work item is routed to the next stage that its type requires

    @scenario_id=SCN-FACTORY-LOOP-005 @status=planned @evidence=spoken @source=04:26
    Scenario: The spec agent writes a specification and drives its approval
      Given a triaged work item that needs a specification
      When the spec agent finishes a draft specification
      Then the specification is attached to the work item
      And a human is asked to review the specification

    @scenario_id=SCN-FACTORY-LOOP-006 @status=planned @evidence=spoken @source=04:32
    Scenario: The implementation agent implements, validates and updates code changes
      Given a work item with an approved specification
      When the implementation agent finishes
      Then a pull request exists for the work item
      And the pull request records which checks the agent ran and their results

    @scenario_id=SCN-FACTORY-LOOP-007 @status=planned @evidence=spoken @source=04:32 @source=09:58

      Given an open pull request created by the factory

      Then each finding is routed either back to rework or to a human for resolution
      And a human can be asked to review the code

    @scenario_id=SCN-FACTORY-LOOP-008 @status=planned @evidence=spoken @source=04:36 @source=12:01

      Given a pull request that changes user-visible behavior
      When the verification step runs
      Then an agent operates the running product through computer use
      And screenshots or a video of the verified behavior are attached to the run

    @scenario_id=SCN-FACTORY-LOOP-009 @status=planned @evidence=spoken @source=04:36
    Scenario: The change ships through the existing CI/CD pipeline
      Given a reviewed and verified pull request
      When the change is merged
      Then it ships through the company's CI/CD pipeline

    @scenario_id=SCN-FACTORY-LOOP-010 @status=planned @evidence=screen @source=03:40

Feature: Data, context and sovereignty
  Run data is the raw material of improvement. The company records it completely

07What the talk leaves open

Questions a real factory must answer that the talk does not. They are the first places to add your own requirements.

  1. How to prove that self-improvement works.He says they are still learning this (15:47). IMPROVE-005 asks for a before-and-after comparison; it still needs a rule for sample size and for when a change is reverted.
  2. Whether the judges can be trusted.Scoring relies on LLM judges, but nothing is said about checking them against human labels. A wrong judge sends self-improvement in the wrong direction.
  3. How replay avoids side effects.Benchmarks replay real tasks “thoughtfully” (19:06). The factory needs fakes or sandboxes for chat, forge, tracker and databases during replay.
  4. Which change needs which human.Human gates exist, but no policy says which risk class needs spec, code or product review, or who may merge a change to the factory itself.
  5. Which direction is good for human interactions per PR.The demo shows 21.5 with no target. Define what counts as an interaction and whether the goal is fewer touches or better ones.
  6. How specifications and acceptance are written.The loop has a spec stage, but nothing on spec format, acceptance criteria or traceability from spec to test to PR.
  7. Security beyond the sandbox.Network egress, secret rotation and prompt injection through tickets, chat messages or web pages are not covered.
  8. How cost is attributed.The total is marked “approximate”. Shared platform cost and scorer cost need an allocation rule before cost per PR can drive decisions.
  9. Whether benchmarks overfit.Suites built from your own past tasks can go stale or be gamed by routing rules. Decide how often suites are refreshed and held out.
  10. What the monitoring stage does.The talk mentions “some aspect of monitoring” and one error webhook. Define which production signals create work and how they link to the change that caused them.
