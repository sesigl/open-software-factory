Quality system · Open Software Factory repository

Factory Quality Gates

How the repository proves that everything works when agents write the code: a Gherkin specification at the root of each module, exactly one outside-in system test per scenario, deterministic checks that the tests exist, pass and stay outside the module, evergreen docs, a few end-to-end smoke tests, and the agent rules that carry the work until the factory can build itself.

1 system test per scenario 0 unit tests by default 22 deterministic checks 5 smoke scenarios 5 bootstrapping phases

Snapshot from 2026-10-18. The Markdown documents in this repository are the source of truth and win where this page differs. Changed since: TypeScript is the only core language (ADR 0009), and the monorepo tooling is pnpm workspaces with Turborepo, not Nx (ADR 0010).

01What a system test may touch

The whole system rests on one boundary. A test drives the built module from outside and checks only what the module produces. Everything the module calls is a fake that the test controls.

Scenario: The evidence bundle is attached to the pull request
  Given a pull request with a Playwright trace
  When the developer runs "proof attach" for the pull request
  Then the pull request has a comment that links the evidence bundle
  And the pull request has a check named "proof" with the result "success"
  • IDs: SCN-<MODULE>-NNN, unique in the repository, from make next-id.
  • Status: planned, implemented or deprecated.
  • Every module's -001 is its README quick start, so the quick start never breaks.
  • Shared port behavior is written once with @conformance; every adapter runs it.

03Deterministic checks

No check calls a model or the network. Each failure prints its ID and the file to fix. The starter kit's docs/quality/checks.md describes every check and how it works.

04Why no unit tests, and what replaces their safety

Unit tests giveCost with agentsReplaced by
Fast feedbackAgents spend many turns keeping hundreds of tests in step with refactorsFast system tests: one artifact start per module, parallel files, fakes instead of real services, BUDGET check
Edge-case coverageTests pin implementation details, so they break on correct changesScenario Outlines with example tables, from the outside; unit tests only where a module's AGENTS.md allows them for a pure algorithm
Confidence that code is exercisedCoverage numbers that agents learn to gameREACH (coverage of the running module during system tests) and nightly MUTATION

Limits: STEPS proves that a test follows the scenario's words, not that it checks their meaning. ASSERT, MUTATION and human review of the first tests in each module close most of that gap. The local hook catches only obvious edits to implemented scenarios; SPECGUARD in CI is the real guard.

06End-to-end smoke tests

Few and stable: they prove the modules work together on the Compose profile. All fakes are deterministic; the forge is a real Forgejo container; the harness is a scripted ACP agent.

SCN-E2E-003A repeated failure becomes a pull request to the factory

09Starter kit

The draft files for the new repository are delivered with this page: AGENTS.md, CLAUDE.md, six skills, .claude/settings.json with the protect-paths hook (tested on four cases), docs/quality/checks.md, docs/explanation/bootstrapping.md and module-tiers.md, the module template with its quick-start scenario and system test, and the five smoke scenarios (all parse with the official Gherkin parser).

Not yet built: the testkit, the check scripts and the Makefile. They are the work of phase 0. The @osf/testkit API in the examples is a proposal.
